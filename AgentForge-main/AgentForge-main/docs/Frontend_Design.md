# Frontend Design

## Current Status

A real frontend exists at `frontend/` — Next.js 16 (App Router, TypeScript), covering four milestones: a dashboard + live workflow view, a repository explorer with a Monaco-based code viewer (now editable), login/register + authenticated requests, and file editing/saving wired to the v1.1 Repository API. It is not the full "AI Operating System" vision (no terminal, no diff viewer in the UI yet, no folder CRUD in the UI yet) — those remain future milestones. AgentForge is now used through three interfaces: the CLI, the REST/SSE API (`backend/api/`), and this frontend, all sharing the same `Application`/API surface — see [API_Design.md](API_Design.md).

---

## Stack

| Concern | Choice |
|---|---|
| Framework | Next.js 16 (App Router, TypeScript, Turbopack) |
| Styling | Tailwind CSS v4 + shadcn/ui (Radix primitives) + `@tailwindcss/typography` for Markdown |
| Motion | Framer Motion |
| Editor | Monaco (`@monaco-editor/react`, dynamically imported with `ssr: false`) — editable, saves via the Repository API |
| Markdown | `react-markdown` + `remark-gfm` |
| Quick-open / search | shadcn `Command` (built on `cmdk`, built-in fuzzy filename filtering) |
| Terminal (future) | xterm.js — not yet integrated |
| Server data | TanStack Query (`@tanstack/react-query`) against the REST API |
| Live data | Native browser `EventSource` against the SSE endpoint — no client library |
| Icons | Lucide |

`NEXT_PUBLIC_API_URL` (`.env.local`, default `http://127.0.0.1:8000`) points the frontend at the FastAPI backend; in production it's set to the deployed API origin via Vercel's environment settings, and `lib/api.ts` is the single source every API call and SSE connection derives from. The backend's `API_CORS_ORIGINS` already defaults to `http://localhost:3000`, matching `next dev`'s default port, so local development needs no extra CORS configuration. See [Deployment.md](Deployment.md) for the full production deployment (Docker, FastAPI Cloud, Vercel, CORS).

## What's Built (Milestone 1)

* **Dashboard** (`/`) — `CreateRunForm` (posts to `POST /api/v1/runs`, redirects to the new run's live view as soon as the run ID is known) and `RunList` (polls `GET /api/v1/runs`, backed by the PostgreSQL run index).
* **Live run view** (`/runs/[runId]`) — `AgentPipeline` (derives each of the 8 agents' pending/active/completed/failed state by scanning the live event stream), `EventFeed` (a live-scrolling, auto-following list of every `WorkflowEvent`, connected via `useRunEvents` — a thin hook around `EventSource`), and `RunSummaryPanel` (polls `GET /api/v1/runs/{id}` for testing/review/file-count once available, stops polling once the run reaches a terminal status).
* **Theme** — a dark "forge" palette (deep charcoal surfaces, an ember-amber accent) defined as CSS custom properties in `globals.css`, deliberately distinct from the generic violet/indigo look most AI products default to. Light mode is not implemented (dark is the only theme for now, matching the original vision's "primary theme should be dark, support light mode later").

Verified against a real end-to-end run (not mocked): a genuine `POST /api/v1/runs` call, real SSE events for all 8 agents streaming into the live view's data model, and the run reaching `completed` with the dashboard/detail endpoints reflecting it correctly.

## What's Built (Milestone 2, superseded by Milestone 4 below)

A repository explorer + code viewer, added as a "Code" tab on the run page alongside the existing "Activity" view (`components/run/run-view.tsx`), sharing the same `useRunEvents` SSE connection rather than opening a second one. Originally shipped **read-only** (the backend had no file-mutation API yet); Milestone 4 made it editable once the backend gained one. The bullets below describe what's still true today; anything superseded is noted inline.

* **File tree** (`components/repo/file-tree.tsx`) — as of Milestone 4, built from the v1.1 `/repo/tree` response (`lib/file-tree.ts`'s `fromRepoTree`), a real nested tree from a live directory scan, not the old flat `written_files` list; expand/collapse, per-extension icons, keyboard navigation (arrow keys + Enter), a context menu with the one action that's actually implemented (copy path) — new/rename/delete file-tree actions are still not wired to the UI (the backend supports them; see "Deliberately Not Built Yet").
* **Monaco editor** (`components/repo/code-editor.tsx`) — dynamically imported (`ssr: false`), a custom `forge-dark` theme matching the app palette, minimap/folding/word-wrap/breadcrumb-free-but-tabbed navigation, automatic JSON formatting on open. As of Milestone 4: editable, with a status bar showing Saved/Unsaved/Saving state, a Save button, and a Cmd/Ctrl+S keybinding registered directly on the Monaco instance.
* **Tabs** (`components/repo/tab-bar.tsx`) — multiple open files, close/close-others/close-all, active-tab indicator, a dirty-state dot per tab (Milestone 4); open tabs + expanded folders + last-active file persisted per run ID in `localStorage` (`hooks/use-persisted-state.ts`).
* **Markdown preview** (`components/repo/markdown-preview.tsx`) — `react-markdown` + `remark-gfm`, preview/split modes (split mode's source pane is the same editable `CodeEditor`, wired the same way); Mermaid code fences render as plain code blocks for now (not wired to a renderer).
* **Quick-open** (`components/repo/quick-open.tsx`) — Cmd/Ctrl+P, filename search (fuzzy, via `cmdk`'s built-in filter) and a content-search mode that fetches+caches file contents on demand via `useQueries` and highlights matching lines. Still client-side, unmigrated to the v1.1 backend search endpoint (`GET /repo/search`) — see "Deliberately Not Built Yet".
* **AI-context inspector** (`components/repo/file-inspector.tsx`) — real data only: which agent materialized the file (always "Developer" — the backend now exposes real per-file `agent` metadata via `GET /repo/files/{path}/metadata`, but this component hasn't been migrated to it yet), run-wide testing/review status (`GET /runs/{id}`), and related project knowledge entries (`GET /runs/{id}/knowledge`, filtered to architecture decisions and coding standards).
* **Live updates** — the explorer's file tree re-fetches (`queryClient.invalidateQueries`) when `agent_completed`, `workflow_completed`, `testing_passed`, or any of the v1.1 repository events (`file_created`/`modified`/`deleted`/`renamed`, `folder_created`/`deleted`) arrive on the page's existing SSE stream.

Verified against a real prior run's materialized files (nested paths, multiple extensions) — file list and nested-path content retrieval confirmed against the live backend. Monaco's actual in-browser rendering/interactions were not visually verified — no browser automation tool is available in this environment; typecheck, lint, and production build are all clean.

## What's Built (Milestone 3: Auth, v1.1)

The backend's JWT foundation (`/auth/register`, `/auth/login`, `/auth/me`) went from unenforced to mandatory on every resource route in v1.1 (see [API_Design.md](API_Design.md)). Before that change landed, the existing frontend had no login UI and attached no token to any request — so enforcing auth backend-wide would have broken the dashboard, live run view, and repo explorer outright. This milestone closes that gap:

* **`AuthProvider`** (`components/providers/auth-provider.tsx`) — React context wrapping the whole app (in `app/layout.tsx`, inside `QueryProvider`). On mount, reads a token from `localStorage` and calls `GET /auth/me` to confirm it's still valid before trusting it; exposes `login`/`register`/`logout` and a `status` (`"loading" | "authenticated" | "unauthenticated"`).
* **Token storage** (`lib/auth-storage.ts`) — plain `localStorage` under `agentforge_token`, read/written outside of React so `lib/api.ts`'s `request()` can attach it synchronously to every fetch call without needing a hook.
* **Login/register page** (`app/login/page.tsx`) — a single page, tab-toggled between sign-in and create-account, using the existing shadcn `Card`/`Tabs`/`Input`/`Button` components to match the rest of the app rather than introducing new styling.
* **Route gating** (`components/shell/app-shell.tsx`, now a client component) — redirects to `/login` when unauthenticated (except `/login` itself), and back to `/` once authenticated; shows the signed-in user's email and a sign-out button in the header when authenticated.
* **`lib/api.ts`'s `request()`** — attaches `Authorization: Bearer <token>` to every call when a token is present; on a `401` response, clears the stored token so the next render's auth check redirects to `/login` instead of retrying with a now-invalid token.
* **SSE auth** — `eventsStreamUrl()` appends `?token=<jwt>` to the events URL, since native `EventSource` cannot set custom headers. `hooks/use-run-events.ts` needed no changes: it already builds its `EventSource` from `eventsStreamUrl()`, so the token flows through automatically. This is the frontend side of the backend's deliberately-scoped `get_current_user_for_sse` exception (see [API_Design.md](API_Design.md)).

Verified: TypeScript (`tsc --noEmit`), ESLint, and a production build (`next build`) all pass cleanly; the backend's register/login/me/protected-route flow was verified end-to-end against a running server (register → login → `/auth/me` → a protected route returning 401 unauthenticated and 200 authenticated). The actual in-browser login → dashboard → live-run flow was **not** visually verified — no browser automation tool is available in this environment, so this remains unconfirmed beyond static analysis and the API-level check above.

## What's Built (Milestone 4: Editable Repository)

Milestone 2 shipped read-only deliberately (no backend write support existed yet); v1.1 closed that backend gap but left the UI unwired (documented as a known, scoped-out gap in the v1.1 report). A follow-up request reported "still not able to edit anything" — this milestone closes that gap by wiring the explorer to the v1.1 Repository API:

* **`CodeEditor`** (`components/repo/code-editor.tsx`) — `readOnly` removed. Emits `onChange` on every keystroke; a status bar shows Saved / Unsaved changes / Saving…; a Save button and a Cmd/Ctrl+S command registered directly on the Monaco instance (`instance.addCommand`) both trigger the same save path. `MarkdownPreview`'s split-mode source pane is the same component, wired identically.
* **Draft tracking** (`components/repo/repo-explorer.tsx`) — unsaved edits live in a `drafts: Record<path, content>` map in `RepoExplorer`, not inside `CodeEditor` itself, because the editor remounts (`key={path}`) on every tab switch and would otherwise lose in-progress edits. The displayed content is `drafts[path] ?? savedContent`; dirty state per path is computed by comparing the draft against TanStack Query's cached server content for that path (`queryClient.getQueryData(["repo-file", runId, path])`), so it stays accurate across tab switches without an extra fetch.
* **Save** — `PUT /repo/files/{path}` via a `useMutation`, sending the file's `version` (from the last read) as `expected_version` for optimistic-concurrency. On success, the query cache is updated in place (`queryClient.setQueryData`) and the draft is cleared. On a `409` conflict (someone/something else changed the file since it was read), a toast offers a "Reload" action that discards the local draft and refetches.
* **Data source migrated** to the v1.1 Repository API throughout: `GET /repo/tree` (live directory scan, replacing the old flat `GET /runs/{id}/files`) and `GET /repo/files/{path}` (replacing the old read-only `GET /runs/{id}/files/{path}`) — `lib/file-tree.ts` gained `fromRepoTree()` to convert the new nested-tree response shape into the same `FileTreeNode` type the tree UI already used, so `FileTree`/`flattenFiles`/`ancestorFolders` needed no changes.
* **Tab bar dirty indicator** (`components/repo/tab-bar.tsx`) — a small dot next to the filename on any open tab with unsaved changes; closing a dirty tab (via the X, Ctrl/Cmd+W, or "Close all") prompts for confirmation before discarding.
* **Quick-open and the AI-context inspector were intentionally left on the old data paths** in this pass (`getFileContent`/`listKnowledge`/`getRun`) — they're read-only, unaffected by the "can't edit" report, and migrating them (to backend-powered search, and to the new per-file `agent`/`generated_by_ai` metadata) is scoped separately below rather than bundled in reactively.

Verified: TypeScript (`tsc --noEmit`), ESLint, and a production build all pass cleanly. The save flow's backend half (`PUT /repo/files/{path}` with `expected_version`, including the 409-conflict path) is covered by the existing backend test suite (`tests/test_api_repository.py`). The actual in-browser typing → saving → reload-persists flow was **not** visually verified — no browser automation tool is available in this environment; this is disclosed rather than assumed.

## What's Built (v1.2: Download Action + Documentation Persistence)

Generated documentation needed to be a durable, browsable/editable project artifact (see [API_Design.md](API_Design.md)'s "Documentation Persistence" section) — since it's now just a regular file under the run's output directory, it already shows up in the tree, opens in Monaco, previews as Markdown, and saves through everything Milestone 4 built, with **no new frontend code required for any of that**. The one real gap closed on the frontend side was download, which the backend spec required as a generic file capability:

* **Download** (`components/repo/tab-bar.tsx`'s context menu, wired from `RepoExplorer.handleDownload`) — client-side only, no new backend call in the common case: uses the tab's unsaved draft if one exists, else TanStack Query's cached content for that path, else falls back to a fresh `GET /repo/files/{path}`. Builds a `Blob`, triggers it via a synthetic `<a download>` click. Deliberately generic (works for any open file, not just docs) rather than wired to the backend's documentation-specific `/repo/documentation/{path}/download` route, per the "no special-case frontend logic" requirement.

Verified: TypeScript, ESLint, and a production build all pass cleanly.

## What's Built (v1.4: MCP Management + Workflow Resume UX)

Two independent additions, both exposing backend capability that already existed but had no UI:

* **MCP Servers page** (`/mcp`, `components/mcp/`) — a `Servers` list (connection status, transport, tool count, auth type, cached health-check result) and a `Tool Explorer` (every registered tool, filterable by name/description, grouped by server), backed by `GET /api/v1/mcp/servers`/`/tools` and a manual `POST /servers/{name}/health-check`/`POST /refresh`. Inspection-only — no tool-execution UI, matching the backend's own scope.
* **Resume UX** — a `ResumeButton` on dashboard run cards and the run detail header (shown once a run's status is resumable and its SSE connection has gone stale, not while it's actively streaming), a "Continue Working" dashboard section (superseded by the v1.5 project-grouped sections below), and a `RecoveryPanel` on the run detail page (failure reason, last completed agent, resume action) for `failed`/`waiting_for_user` runs. `useRunEvents` gained a `reconnect()` (generation-counter-driven remount) so resuming a run whose SSE connection had already closed reconnects cleanly instead of needing a full page reload.

## What's Built (v1.5: Dashboard, Iterative Development, IDE Polish)

The largest frontend change since the initial milestones — turns the one-shot generator into a persistent, conversational IDE. See [API_Design.md](API_Design.md#projects--iterative-development-v15) and [Agent_Design.md](Agent_Design.md#iterative-development-v15) for the backend half.

* **Project workspace** (`/projects/[projectId]`, `components/workspace/project-workspace.tsx`) — the new primary route, five tabs: **Chat** (default), **Repository** (the existing `RepoExplorer`, unchanged, just pointed at the project's latest run), **Activity** (existing `AgentPipeline`/`EventFeed`), **Docs**, **Knowledge**. `/runs/[runId]` (`RunView`) is kept **unchanged** as a legacy deep link — the two routes coexist; nothing about the run-level view was touched.
* **Chat** (`components/chat/`) — `ChatPanel` owns the conversation query (`GET /projects/{id}/conversation`) and a `continueProject` mutation; `MessageList` renders history (user messages as plain bubbles, assistant messages through `ReactMarkdown`+`remark-gfm`, the same library `MarkdownPreview` already used — no new dependency); `Composer` (Cmd/Ctrl+Enter to send); a `useLiveStatus` hook (a lighter-weight sibling of `useRunEvents`, single-status-line rather than full history) drives a "Developer agent working…" style live status line while a follow-up run is in flight, translating the same SSE events `EventFeed` shows via a shared `lib/event-labels.ts` (extracted from `EventFeed`'s inline label logic, now used by both). **Not built**: true token-by-token streaming of the assistant's reply — the backend has no LLM streaming to expose (see [Agent_Design.md](Agent_Design.md#iterative-development-v15)); the chat instead shows staged live-status during the run and the final synthesized reply once it completes.
* **Dashboard rewrite** (`app/page.tsx`) — `CreateRunForm` now posts to `POST /api/v1/projects` and redirects to `/projects/{id}`. `ContinueWorking` is now four independent, small, still-polling sections (Continue Working / Running / Failed / Recently Completed) built on a shared `ProjectGroupSection`, each its own `["dashboard-projects", status]` query — deliberately **not** sharing a cache key with the main table below, since a paginated/filtered query key can't be reused for an unpaginated "top 5" section. The main list (`ProjectTable`, replacing `RunList`/`RunCard`, both deleted) is a real paginated table: `FilterBar` (status multi-select, free-text search, date range, sort — all via the upgraded `GET /projects`) and `PaginationControls` (page-size selector, Prev/Next, computed from the response's new `total_count`/`has_more`), keyed `["projects", {status, q, dateFrom, dateTo, sort, page, pageSize}]` with **no** polling (unlike the grouped sections above it — polling a page the user is actively reading would yank their scroll position).
* **Repo/editor polish** (`components/repo/`) — a `BreadcrumbBar` above the editor (clicking a folder segment reveals+scrolls it in the tree, reusing a generalized `revealPath()`); a word-wrap toggle and a toolbar Download button on `CodeEditor` (Monaco already provided independent scrolling and Ctrl+F find for any file — the gap was UI affordances, not a new preview component, so no separate "plain text" renderer was built); `QuickOpen` gained "Current file" (searches already-loaded content, no network call) and "Markdown" search scopes alongside the existing Files/Content modes; `TabBar` gained Pin/Unpin (pinned tabs exempt from Close Others/All, rendered first) and a "Recently Closed" restore dropdown in the Files panel header. Tab/pin/expanded state is now keyed by a `storageKey` prop (`RepoExplorer`'s new optional prop, defaulting to `runId`) — the project workspace passes `projectId` instead, so open tabs survive a follow-up message creating a new `run_id`; the legacy `/runs/[runId]` route is unaffected (no `storageKey` passed, falls back to the old `runId`-keyed behavior).
* **Tab reordering is context-menu-based ("Move left"/"Move right"), not drag-and-drop.** The spec asked for drag-and-drop; this was a deliberate substitution, disclosed rather than silently downgraded — with no browser automation available in this environment to verify drag physics (z-index, touch vs. mouse, layout thrashing are all real, easy-to-get-subtly-wrong failure modes), a keyboard/screen-reader-accessible context-menu action was judged the more defensible choice over an untestable gesture integration between Radix's `ContextMenu` and Framer Motion's `Reorder`.
* **Split-view scroll sync** (`MarkdownPreview`) — the Markdown source (Monaco) and rendered preview panes now scroll together, percentage-based, in both directions. Required a new `onEditorReady` escape-hatch prop on `CodeEditor` (exposes the live Monaco instance to a parent that needs it, e.g. for this) since `CodeEditor` didn't expose scroll state itself.

The editor's core scroll/flexbox layout bug (Monaco/Markdown preview clipped or double-scrolling depending on viewport) was fixed in an **earlier** pass this same cycle, before the v1.5 spec arrived — `body`/`main`/`RunView`/`RepoExplorer`'s flex-fill chain (`h-full`/`min-h-0`/`overflow-y-auto` at every level) replaced a fragile `h-[calc(100vh-10.5rem)]` magic-number hack. v1.5's repo/editor work builds on top of that fix and does not re-touch it.

Verified: TypeScript (`tsc --noEmit`), ESLint, and the dev server's own compile log are all clean across every new/touched route and component. The full continuation flow (create a project, let it complete, send a real follow-up, confirm the same `output_directory` is reused and files are additive) was verified **live against a real backend with a real LLM** — see the v1.5 Final Implementation Report (`summary/v1.5_summary.md`) for the full transcript. The dashboard/chat UI's actual in-browser rendering and interaction (clicking through tabs, drag/pin gestures, chat scrolling) were **not** visually verified — no browser automation tool is available in this environment; this is disclosed rather than assumed, consistent with every prior frontend milestone's verification notes above.

## What's Built (v1.6: Recovery UX + Reliability Dashboard)

See [API_Design.md](API_Design.md#recovery--failure-analytics-v16) and [Agent_Design.md](Agent_Design.md#failure-classification-per-invocation-analytics-and-recovery-v16) for the backend half.

* **`RecoveryPanel` rewrite** (`components/run/recovery-panel.tsx`) — now fetches `GET /runs/{id}/failure` for real failure detail (failed/last-successful agent, retry counts, classified category/reason, provider/model, a "same failure as last time" badge) and highlights the confidence-scored recommendation rather than listing every action equally. Eight actions: Resume (unchanged `ResumeButton`, hidden for a hard `FAILED` run since `resume_run()` is a documented no-op there); Retry Failed Agent and Restart From Checkpoint (the latter opens a `Dialog` checkpoint picker backed by `GET /runs/{id}/checkpoints`); Restart Entire Workflow and Duplicate & Retry (both project-scoped, only shown when a `project_id` is known — see below — and both navigate to the resulting new run/project on success rather than staying on a now-stale page); View Logs (a `Dialog` reading `GET /runs/{id}/logs`, with a copy-to-clipboard action); View Generated Files / View Documentation (real, distinct hrefs per host — see below, fixing a real pre-v1.6 bug where both pointed at the same tab); Report Issue (clipboard copy of a structured failure summary — no issue tracker integration exists, so this is the honest scope, not a fake backend call).
* **Mounted in `ProjectWorkspace`'s Activity tab, not just `RunView`.** Confirmed gap: the panel existed only on the legacy `/runs/[runId]` route; `/projects/[projectId]` — the actual primary v1.5 landing surface — had no recovery UI at all. Both hosts now pass context-appropriate `filesHref`/`docsHref` (`RunView`'s single Code tab handles both, so `docsHref` is omitted there rather than pointing at the same place as `filesHref` under a different label; `ProjectWorkspace` has genuinely separate Repository/Docs tabs, so both hrefs differ for real).
* **`project_id` now on `RunSummary`/`RunDetail`** (backend addition) specifically so `RunView`, which has no other route parameter carrying it, can pass it down to `RecoveryPanel` and conditionally show the two project-scoped actions.
* **`WorkflowTimeline`** (`components/run/workflow-timeline.tsx`) — a new, small component rendering `GET /runs/{id}/timeline` as an ordered list (agent, status, duration, an "attempt N" badge when `attempt_number > 1`), mounted inside `RecoveryPanel` on both hosts.
* **`useRecoveryProgress`** (`hooks/use-recovery-progress.ts`) — synthesizes staged client-side status text ("Restoring checkpoint…" → "Reloading workflow state…" → "Reconnecting…") across a recovery mutation's lifecycle, since no server-emitted event exists for these client-only mechanics; holds on the final label rather than looping until the caller calls `stop()`.
* **`EventFeed` now filters out `agent_invocation_recorded`** — it fires once per graph node alongside `agent_started`/`agent_completed`, pure duplication in the human-facing activity log (still visible via the workflow timeline and the reliability dashboard, which are where the extra detail is actually useful).
* **`/reliability` dashboard** (`app/reliability/page.tsx`, `components/reliability/reliability-dashboard.tsx`) — a new top-level nav destination. Summary cards (overall success rate, top failure category, top provider) plus a per-agent table sorted failure-rate-first, each row expandable in place (no separate route) to a failure-reason breakdown and up to 5 recent failures, backed by `GET /reliability/summary`/`GET /reliability/agents/{agent}`.

Verified: TypeScript (`tsc --noEmit`), ESLint, and the dev server's own compile log are all clean across every new/touched route and component (the dev server was restarted mid-session since a brand-new top-level route directory, `/reliability`, wasn't picked up by an already-running long-lived process — a known Next.js dev-server route-discovery limitation, not a bug in the new code). Backend-side recovery mechanics (the LangGraph `get_state`/`update_state`/`as_node` sequence every recovery mode is built on) were verified against real infrastructure — see `tests/test_recovery_checkpoint.py` and the note in [Future_Improvements.md](Future_Improvements.md#recovery--reliability-v16). The panel's actual in-browser rendering and interaction were **not** visually verified — no browser automation tool is available in this environment, consistent with every prior frontend milestone's verification notes.

### v1.6.x — Workflow Progress Graph Consistency Fix

`AgentPipeline`'s `deriveStates()` (`components/run/agent-pipeline.tsx`) derived each node's displayed status independently from raw event history, with no dependency-order enforcement between nodes — so a downstream node's stale "completed" mark from an earlier attempt (a prior repair loop, or a run that predates the `static_validation` node's introduction) could persist and render as complete even while an upstream node the real graph structurally requires first had never completed. Root-caused against a real run's actual recorded `workflow_events`, not assumed — see [Agent_Design.md](Agent_Design.md#v16x--workflow-progress-graph-consistency-fix) for the full writeup and the (real, not synthetic) before/after data. Two changes:

* **`deriveStates()` now enforces the dependency rule directly**: every `agent_started` event resets that node and everything after it (in pipeline order) to "pending" before marking the started node "active" — a node can only ever display "completed" if it's the *current* pass's completion, never a leftover from an earlier cycle. This also correctly fixes the general retry/repair case (e.g. `reviewer`'s prior-attempt "completed" mark now correctly clears the moment `developer` restarts for a repair), not just the specific historical-run case that surfaced it.
* **`AGENT_PIPELINE` (the hand-maintained node-order constant) was removed** from `lib/types.ts` as the source of truth and replaced by `getWorkflowGraph()` (`GET /api/v1/workflow/graph` — see [API_Design.md](API_Design.md#workflow-graph-v16x)), fetched once via `useQuery` (`staleTime: Infinity`, since topology doesn't change at runtime) in `AgentPipeline` itself. A `FALLBACK_AGENT_PIPELINE` constant remains, but only as a loading-state placeholder before the fetch resolves — explicitly documented as not authoritative. `AGENT_LABELS` (human-readable display names) stays frontend-only and degrades gracefully for an unrecognized agent (humanizes the raw snake_case name) rather than rendering nothing, so a future backend-only node addition doesn't require a frontend change to avoid a blank label — though it also won't get a hand-tuned label until one is added, a disclosed, low-stakes gap.

Verified two ways beyond `tsc`/`eslint`: (1) a standalone reimplementation of the exact algorithm run against realistic event sequences covering every scenario in the bug report (successful run, validation failure, mid-repair retry, and — most importantly — a resume of a run whose event history genuinely predates `static_validation`, built from this project's own real database), and (2) the *actual* recorded event history for a real run in this project's own database run through both the old and new algorithm side by side, concretely showing the old algorithm marking `tester`/`debugger`/`reviewer` all falsely "completed" while the new one correctly resets them to "pending." No frontend test runner is configured in this repo, so this is a Node script, not an integrated test suite — disclosed rather than silently substituted for one.

## What's Built (v1.7: Production Deployment)

The frontend and backend both moved from local-only to a real production deployment (Vercel and FastAPI Cloud respectively) — see [Deployment.md](Deployment.md) for the infrastructure side. This entry covers the frontend-code changes that made a deployed, cold-starting backend a good experience rather than a silent failure:

* **`wakeBackend()`** (`lib/api.ts`) — a fire-and-forget `fetch` to the backend's root, called once per page load from a module-level flag + empty-dependency `useEffect` in `components/shell/app-shell.tsx` (resilient to React 18 StrictMode's dev-mode double-invoke). Exists because FastAPI Cloud's free tier cold-starts after inactivity; this nudges the backend awake as early as possible rather than waiting for the user's first real request to pay that cost.
* **Fetch-failure UX on the dashboard.** `ProjectGroupSection` previously handled `isLoading` only — a fetch failure (backend still cold-starting, or genuinely unreachable) rendered nothing at all. It now has a dedicated `isError` branch: a "Couldn't reach the backend, it may still be starting up" message with a Retry button (`query.refetch()`). `ProjectWorkspace`'s existing project-load error state got the same Retry button and reworded copy.
* **No new SSE reconnect logic was needed.** Native `EventSource`'s built-in reconnect, combined with `EventFeed`'s existing `"Reconnecting"` label for the `error` connection state, already presented a transient connection drop as recoverable rather than a permanent failure — confirmed by reading `hooks/use-run-events.ts` and `components/run/event-feed.tsx` rather than assumed.
* **React Query's default retry behavior** (3 attempts, exponential backoff) already gives every `useQuery`-based read baseline tolerance for a slow cold start with zero code change. Mutations were deliberately left without retry, to avoid duplicating a side effect (e.g. creating a project twice) on a retried request that actually succeeded server-side but timed out client-side.
* **Auth switched from username to email.** `app/login/page.tsx` now has a single email field for both sign-in and registration (the separate username field is gone); `UserOut`/`lib/api.ts`'s `register`/`login` signatures dropped `username` entirely. Surfaced during live production testing — real account creation against the deployed backend, not caught by the existing test suite since frontend auth has no automated tests.

Verified: a real `vercel --prod` deployment, a real FastAPI Cloud deployment, and a live CORS check (preflight + actual request, `Origin` header matching the deployed frontend) against the deployed backend. The wake-up ping and retry UX were not exercised against an actual cold-started instance in this pass (no reliable way to force FastAPI Cloud to sleep on demand); the code path itself (a plain `fetch` with a swallowed rejection, and a standard TanStack Query `isError`/`refetch` branch) is the same pattern already verified elsewhere in this codebase.

## Deliberately Not Built Yet

Folder CRUD in the UI (backend supports it; no create/rename/delete/move affordance in `FileTree`'s context menu yet), a visual diff viewer (`GET /repo/files/{path}/diff` exists; no Monaco Diff Editor integration yet), migrating quick-open's Repository/Markdown modes to backend-powered search (`GET /repo/search`, including fuzzy mode — v1.5 added scope *modes*, not a backend migration; content search is still a client-side per-file fetch-and-scan), migrating the AI-context inspector to the new per-file `agent`/`generated_by_ai`/`last_edited_by` metadata instead of the current hardcoded "Developer agent" text, and Mermaid rendering. True drag-and-drop tab reordering (v1.5 shipped a context-menu-based substitute — see above) and true token-by-token chat streaming (v1.5 shipped staged live-status instead — see above) are both explicit, disclosed scope trims, not oversights. A CLI counterpart to `POST /projects`/`POST /projects/{id}/messages` (`agentforge create` remains one-shot-only). Beyond that: integrated terminal, command palette (beyond quick-open), right-click-to-everywhere polish, workflow visualization beyond the linear agent pipeline, architecture map, live collaboration polish, light mode, resizable panels, mobile/narrow-viewport layouts for the IDE-style three-pane explorer (treated as out of scope the same way VSCode/Codespaces don't meaningfully support a mobile code editor either). These are real, scoped-out follow-up milestones, not abandoned ideas — see [Development_Roadmap.md](Development_Roadmap.md).
