# Development Roadmap

## What This Document Is

A record of what's actually been built, version by version, plus what would come next. Unlike [Project_Vision.md](Project_Vision.md) (the aspirational full-platform vision) this document tracks real, shipped increments — each one verified with a full test-suite run and a written implementation report in `summary/`.

## Near-Term Candidates

Listed roughly in order of what the current architecture is already closest to supporting — none of these are committed or scheduled, and none should be started without the same repository-assessment-first discipline every batch above followed.

* **MCP access for more agents.** The permission model (`MCPPermissionPolicy`) already supports per-agent grants; extending beyond Documentation is a configuration change plus per-agent risk review (see [MCP_Integration.md](MCP_Integration.md) for why Documentation was chosen first).
* **Additional MCP transports.** SSE transport is a real FastMCP capability not yet exercised by AgentForge. Authentication landed in v1.4; `oauth`/`mtls` are declared but not wired to a transport yet.
* **Frontend: diff viewer, folder CRUD, backend-powered content search.** Editing landed in milestone 4; download landed in v1.2; a documentation-specific browsing tab and search-scope modes (current file/markdown) landed in v1.5. The diff viewer against `/repo/files/{path}/diff`, folder create/rename/delete/move in the file tree's context menu, and migrating quick-open's content search to `/repo/search` (it currently fetches+scans files client-side) are all real, scoped next steps — see [Frontend_Design.md](Frontend_Design.md).
* **True token-by-token chat streaming.** v1.5's project chat shows staged live-status (translated SSE agent-stage events) plus a synthesized final reply, not incremental LLM output — `LLMService` has no streaming support today; adding it would touch every agent's LLM call path, a materially larger change than v1.5's scope.
* **True conditional graph stage-skipping for narrow follow-ups.** v1.5's iterative-development follow-ups always run the full 8-stage pipeline with an intent hint (see [Agent_Design.md](Agent_Design.md#iterative-development-v15)), not a rewired graph that jumps straight to, say, the Tester/Debugger nodes for "fix this bug." Real conditional entry points into `WorkflowBuilder` would be the next step if the full-pass cost becomes a real problem.
* **A written v1.4 implementation report.** Process gap, not a missing feature — see the Shipped table note above.
* **Multi-instance API deployment.** Current SSE delivery and rate limiting are both direct in-process/in-memory implementations — correct for exactly one API server process, not for a horizontally-scaled deployment. Redis (already a dormant `requirements.txt` dependency) is the natural mechanism for both if this becomes necessary.
* **Deeper static validation.** v1.6's `static_validation` node deliberately only checks syntax, local-module imports, and FastAPI route registration — cross-checking Pydantic schemas against SQLAlchemy models (the exact bug class that motivated v1.6), deep relationship/migration validation, and general static analysis (mypy/ruff-in-the-loop) are the natural next step once the narrower pass proves out. See [Agent_Design.md](Agent_Design.md#static-validation-v16--a-ninth-graph-node-not-a-ninth-llm-agent).
* **Workspace restore from a `.backups/` snapshot.** `restart_workflow` writes one, but nothing reads it back today — recovering from a bad restart is a manual filesystem operation. An API endpoint (and frontend affordance) to list/restore a project's backups would close this.
* **A real "Report Issue" backend.** v1.6 scoped this to a clipboard-copy of a structured failure summary, since no issue-tracker integration exists or is being built — wiring it to GitHub Issues or a similar tracker is a real, separate integration.

## Explicitly Not Planned Soon

Carried forward from [Project_Vision.md](Project_Vision.md)'s original non-goals, still true:

* Full autonomous operation without human review of generated output.
* Multi-tenant SaaS features (organizations, teams, billing).
* A plugin marketplace or third-party agent ecosystem.
* Deployment automation / CI-CD generation as a built-in capability.

---

## How This List Changes

A capability moves from "Near-Term Candidates" to "Shipped" only after: a repository assessment confirms it doesn't duplicate existing services, an implementation report is written to `summary/`, and the full test suite passes with zero regressions — the same bar every version in the Shipped table already cleared.
